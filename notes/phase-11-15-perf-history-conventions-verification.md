# Phase 11–15 Notes — Performance, History, Conventions, Verification, Synthesis

## Performance & scalability (Phase 11)
Hot paths:
1. POST /v1/forecasts / /v1/friday/forecast / /v1/predictions/predict — model fitting dominates. Measured live: 7.7s wall for one 24h forecast (14d lookback, candidate backtests incl. AutoARIMA/AutoETS ~4.5s each per selection.py docstring; prior 8.7s event-loop freeze documented in cpu.py). Mitigations in place: run_cpu thread + per-loop semaphore (CPU_SLOTS = cpu_count, env FUTURIS_CPU_SLOTS), cpu_saturated() skips expensive candidates (selection_degraded recorded in model_metadata), model_budget_seconds deadline, cheap-candidates-first ordering, naive fallback if all fail.
2. GET /v1/predictions/matrix + refresh-all — up to 18 pipeline fits; bounded by REFRESH_BUDGET_SECONDS=15 + WRITE_GRACE 2s; sequential; session rollback recovery on cancel.
3. GET /v1/market/forecast — serial outbound calls (IntelX → Stratex → Inference → Memora → Stratex dispatch); each bounded (research 1.5s, peers 6s circuit-broken, memora 3s ×2).
4. Scheduler jobs share the SQLite write lock with request traffic.

DB query patterns:
- list_forecasts: loads ALL rows (list_by_status/list_by_target unbounded) then filters/slices in Python — `limit`/`offset` are NOT resource bounds (forecasts.py:208-255). N rows loaded per request. Finding (perf).
- list_resolved_with_forecasts: limit 5000 default; calibration endpoint loads up to 5000 pairs per call.
- point_in_time_query: scans latest 200 forecast_created events then replays — O(events), no target index on forecast_events.payload (payload is JSON; target only in payload) — works but fragile at scale.
- get_by_idempotency_key: indexed. list_by_target/status: indexed (target+as_of, status).
- No N+1 in repository layer (evidence_refs lazy="selectin" — one extra query per forecast list, acceptable).

Caching: LLM response cache (in-memory, SHA-256 prompt key); idempotency replay (DB); NO cache for forecasts/matrix/evaluation; webhook subscriptions in-memory.
Blocking work: all CPU-bound work goes through run_cpu (asyncio.to_thread) — good. IntelX fetch on event loop but timeout-bounded. Parquet writes synchronous inside CPU-gated section.

What breaks first at 10× load (ranked):
1. CPU saturation on model fitting — bounded by CPU gate; symptom: queue waits (CPU_QUEUE_WAIT_SECONDS), selection_degraded forecasts, latency ↑ linearly. Not a crash.
2. SQLite single-writer lock — scheduler + self-healing + API writes contend; busy_timeout 30s then 503 storage_busy (observed historically per seed-guard docstring). The demo seed holds the lock for a full 180-day run (single-flight guarded now).
3. Anonymous heavy reads (market GET, matrix backfill, ecosystem/peers) — unbounded fan-out to external peers; circuit breakers mitigate; still latency/egress cost.
4. In-memory rate limiter / idempotency / subscriptions — per-process; horizontal scaling diverges (duplicate webhook deliveries, idempotency misses → duplicate forecasts under multi-worker).
5. Postgres path (asyncpg) untested in this sandbox — pool_pre_ping set; untested.
Quick wins: (a) SQL LIMIT/OFFSET + COUNT for list_forecasts; (b) cache matrix/peers with short TTL; (c) require auth on GET market forecast; (d) persist webhook subscriptions; (e) Redis-backed rate limit/idempotency for multi-worker; (f) move scheduler off synthetic connector to configured connector; (g) prepared cache of candidate backtests (rolling warm starts — mentioned in AUDIT_REPORT as mitigation).

## Synthesis (Phase 15)
- Narrative: FUTURIS is a single-author, 6-week-old, single-process calibrated forecasting platform with an unusually strong honesty/provenance culture: every number is labeled live/derived/synthetic/demo; fabricated data was systematically removed after the 2026-10-05 audit; the prediction≠authorization invariant is enforced in schema, validators, and route guards. Architecture: layered modular monolith (api → core → features/models/evaluation/scenarios/evidence → storage → infra) with a hardening layer (upgrade/). Weaknesses: single-writer SQLite ceiling, in-memory everything, anonymous compute-heavy reads, default credentials in examples/connectors, thin UI (one real page), single-writer bus factor, decorative CI lint gate.
- Self-check answers (all 16) are embedded in REPO_ANALYSIS.md sections.
- Confidence: high on architecture/API/security (executed), high on tests/CI (executed), medium on performance-at-scale (reasoned + measured single-request), medium on UI (static; no npm build run), low-medium on production Render behaviour (config read, not deployed).
